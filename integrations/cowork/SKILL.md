# Flight Fare Research (Cowork variant)

Research bookable flight choices for fixed or flexible dates. Compare traveler count, dates, airports, cabin, baggage, currency, and mandatory fees. Treat a search-result price as an observation, not a guaranteed fare. This variant is standalone for the Cowork built-in browser; use its native navigate / find / read_page / javascript_tool / computer click actions rather than a browser CLI.

**Working efficiently:** read results with one `javascript_tool` call returning the main content's `innerText` rather than screenshot-then-read; batch predictable actions; after any layout reflow or viewport change, take a fresh screenshot before any coordinate click, and prefer DOM-scoped lookups over coordinates.

## Choose the workflow

- **Quick path:** fixed dates, one requested cabin, short/medium haul, and no flexible dates, fixed event, stopover, or route-hack request.
- **Full path:** flexible dates, several requested cabins, long-haul, a fixed event, stopover, or an explicit route-hack request.

Quick path order: capable connected search or Google Flights, airline-direct baggage qualification, one independent OTA cross-check, then one permitted nearby-airport check. Skip FlightList, ITA Matrix and the full hack matrix. State the chosen path and any deliberate skips. Search and report **only the cabins requested**; if none is requested, state an economy assumption rather than silently running three cabins.

## Search parameters and time rules

Use only the origins, currency, nearby gateways and per-direction duration limits specified or confirmed for the current request. Do not infer a home location or persistent travel profile. State any assumptions before searching. Enforce the requested cap independently on outbound and return; a strict cap excludes equality. An explicitly requested multi-day stopover overrides only its continuous elapsed span, not each flown city-pair cap. Display local times and durations as `HH:MM:SS`; identify next-day arrivals. A return date means departure from the destination unless an arrival-home deadline is specified.

## Workflow steps

1. **Pin the search contract.** Record travelers, origin and destination, outbound/return dates, target trip length, cabin(s), checked/cabin bags, currency, acceptable flexibility, any fixed event and required pre-event local sleeps, a hard per-direction duration cap if any, and whether the user wants destination planning or fares only. Do not add sightseeing or a day-by-day itinerary unless requested. If the user names a country or region rather than an airport, search the practical airports.

2. **Discover connectors and sources.** Check which travel-source capabilities are present: any connector (Kiwi.com, Expedia, lastminute.com are examples, never assumed installed or connected), its connected status, authorization, and whether it supports exact-date flight shopping with coverage, currency, baggage fields, and quote freshness. Never assume a connector is connected. Prefer a suitable connected connector first; a blocked public website does not establish connector failure. Fill gaps with browser sources and disclose unavailability. Never ask for or accept secrets in chat.

3. **Collect exact-date live results.** Use the tool appropriate to the source. Decline non-essential cookies on every site (`Reject all`, `Continue without agreeing`, or equivalent); a consent screen is not a bot block. Set every search dimension explicitly and verify the rendered page repeats the exact route, dates, traveler count, cabin, and currency before recording any price. Save retrieval time and source URL, round-trip price/currency, airlines, departure/arrival airports and local times, stop count, elapsed duration, airport changes, overnight arrival, cabin mix, baggage state, and whether the price is a headline list fare or a completed-itinerary quote. A loading shell, route teaser, cached monthly minimum, CAPTCHA, or bot page is not an exact-date quote.

   For a fixed-length flexible trip, enumerate **rolling matched pairs** before searching: e.g. "10 days, from 5-15 through 10-20 March" gives 5-15, 6-16, 7-17, 8-18, 9-19, 10-20 - six exact windows per origin/cabin, with the fixed event inside every pair. Build a broader Cartesian product only when the user accepts shorter/longer trips; save every pair and verify the count programmatically. A calendar heatmap or date-grid minimum is not a substitute for exact-date results.

4. **Qualify baggage and fare families.** Select both outbound and return before judging the fare; a cheap outbound does not qualify when every compatible return breaches the duration cap. Classify baggage as exactly one of:

- **included** - itinerary or fare family explicitly includes at least one checked piece;
- **fee required** - the completed page explicitly says the first checked bag costs extra;
- **unverified** - no itinerary-level allowance is exposed, or a range whose lower bound is zero (e.g. `CHF 0-104`) leaves allowance and amount uncertain. A zero lower bound proves neither inclusion nor a required fee; use **fee required** only when an itinerary-specific positive charge or explicit paid-bag requirement is proven.

Never label bag included from airline norms, cabin expectations, or a generic policy page. Expand branded fare families when the booking card exposes them; if `View options` is absent, off-screen, inert, or exposes no usable family/baggage detail after one bounded attempt, go to the airline booking engine. Compare the cheapest bag-inclusive family with base plus explicit bag fee; recommend the lower qualifying total. If the completed page says the price changed, use the completed provider total and retain the old amount only as a clearly labelled stale observation.

**Google Flights fast link (dated user-observed):** the optional fast path is a URL-encoded natural-language `q` link: `https://www.google.com/travel/flights?q=Flights%20from%20ZRH%20to%20LIS%20on%202026-11-05%20through%202026-11-12%20economy&curr=CHF&hl=en`, replacing route, dates, cabin, currency. This is a navigation hint, not a stable API. After it loads, verify in the form header that round-trip mode, airports, both dates, traveler count, cabin, currency, and populated exact-date results are correct; if parsing is wrong or results are absent, use the normal form. This was user-observed on 2026-09-23, not a current verified fare.

5. **Compare cabins honestly.** Search each requested cabin separately and preserve mixed-cabin labels (`Economy + Premium Economy`, `Business + Economy`); do not shorten them to the higher cabin. Prefer a slightly higher pure-cabin itinerary over a misleading mixed-cabin headline.

6. **Cross-check and rank.** Use at least two independent live source families when accessible (e.g. a connector plus Google Flights completion, then airline-direct). Two frontends backed by the same inventory or redirect chain are not independent; disclose the relationship. On an explicit bot page, CAPTCHA, Cloudflare block, 403, or provider guard, make one recorded attempt, mark it blocked, and move on. Do not loop retries or install/configure anti-detection tooling. If only one exact-date source remains, say so plainly and downgrade confidence. Cite only pages actually retrieved, giving source name, URL (or connector identity/query/offer ID), retrieval timestamp with timezone, and the exact claim supported; never cite a blocked page as fare evidence. Distinguish current observations, policies, historical user reports, and unvisited navigation links.

7. **Run route hacks (quick vs full).** Quick path: one practical nearby-airport check when permitted (record why not otherwise). Full path: use WebSearch if available for stopover programs, fifth-freedom routes and current deals, then reprice exact dates; test split one-ways, multi-city/open-jaw, nearby gateways, alternate destination gateways, and provider/fare-family arbitrage against the same matched windows and cabin. Disclose separate-ticket protection, baggage reclaim/recheck and airport changes; reject impossible positioning connections. Show all-in totals (long-haul, required bag, rail/positioning, hotel, transfers), break-even positioning budget, added days, and risk. Reject hidden-city ticketing when checked luggage is required. For stopovers, price the carrier's official tool first, then an open-jaw-plus-local fallback, and never transfer baggage allowance across separate tickets; verify the carrier's over-24-hour rule and entry permission against the traveler's actual passport.

## Event-anchored planning

For weddings, interviews, races, or conferences: calculate the event's local weekday and time-zone offset before searching. Search exact-length matched pairs first, prefer arrival at least three local sleeps before the event (four for an eastward shift of roughly six or more hours), and keep the day before the event low-intensity. Ground any acclimatisation advice in an authoritative health source; do not prescribe medication. Include only the timing needed to justify the travel window.

## Source recipes (inline)

These are workable patterns from prior runs; verify a fresh exact-date result each time, because public frontends change.

- **Google Flights.** Prefer the optional `?q=` fast link above and verify the form header. When driving the full form, open `https://www.google.com/travel/flights`, decline optional cookies, set origin/destination and the two dates, then click the search button. Verify a `/travel/flights/search` page that repeats the route and dates, with a result count and populated fare cards. To complete a round trip, prefer clicking the visible flight card over an off-screen `Select flight` element (verify each card selection actually advances to the expected direction); afterwards check the page title - a return-direction heading such as `Lisbon to Zürich` means the return list, while `Round trip to …` means the booking page. On the booking page capture `Lowest total price`, the provider quote, and the exact baggage wording. If `View options` shows no family detail, go to the airline's own engine.
- **eDreams.** Decline optional cookies (`Continue without agreeing` or equivalent). eDreams restores the previous search into the form, so read back every field rather than trusting pre-filled values. Identify the visible **main flight-search form** and scope all field lookup inside it, because `Where from?` matches two inputs - a Prime deals widget lower on the page also matches and typing there does nothing. Pick the airport autocomplete item that contains the airport name AND the IATA code, then verify the field reads the airport name. Dates cannot be typed (readonly): click `Departure`, wait for hydration, then retry once only if the calendar is closed, use the next-month arrow until the target month/year title is visible (bound this to the needed advances plus one), then click the day whose direct text node equals the day number (a cell's full text can include a fare, e.g. `1€107`) inside the calendar whose `.odf-calendar-title` matches the month/year. Set the dates one at a time: pick the departure day and read back `Departure`; then click the `Return` field explicitly (the calendar does not always switch to the return date by itself, especially when dates were pre-filled, and a second click would overwrite the departure) and pick the return day. Read back both input values (e.g. `Thu, 05/11` and `Thu, 12/11`) before submitting. Submit with `Search Flights` (not `Search Flight + Hotel`). After the summary bar appears, select the ranking tab you need and read the flight cards; if cards are absent, try the ranking tab and one bounded scroll, then inspect the main content. Compare `Regular price` (non-membership) and reprice at checkout.
- **Airline direct (e.g. TAP).** User-observed starting URL: `https://booking.flytap.com/booking/flights/deeplink?origin=ZRH&destination=LIS&depDate=05.11.2026&retDate=12.11.2026&adt=1&chd=0&inf=0&yth=0&language=en&market=ch&flightType=return`. Replace route, dates and passengers; verify cabin, market and actual currency in the results. No current fare is implied. Set origin/destination/dates/travelers, verify the itinerary heading, and pull per-direction prices; TAP prices each direction separately, so sum them. Fare families (e.g. Discount = hand baggage only, Classic = 1 hold bag, Plus = bag + flexible) expand when you click the `Economy` price box on a flight card (a button named like `Economy from 71.4 CHF`; these render only after the cards scroll into view, so scroll first, then `find` "Economy from" - buttons appear in flight order); choose a family's `Select`, then repeat for the return, and read the running total at the top of the page. Stop before `Continue` (no passenger data). Capture family name, per-direction and round-trip totals, and explicit bag state. Other carriers are unverified until tested.
- **FlightList (full path only, discovery).** Type into `#from-input` / `#to-input`, then click the `.eac-item` whose text contains the exact `(IATA)`, never simply the first item; verify `#from-data` / `#to-data` read `airport:<IATA>`. If no suggestions appear, delete and retype the last character. Set `#type`, `#class`, `#currency`, `#checkedbags` explicitly. Dates: click the range field, move to the month, and click the day twice so start = end, then `Apply`; do this separately for departure (`#deprange`) and return (`#retrange`). Before searching, read back both pickers with `jQuery('#deprange').data('daterangepicker').startDate/endDate` (same for `#retrange`), because a misclick lands on a neighbouring day. If screenshots fail (app window hidden), select days in script instead: dispatch `mousedown` then `mouseup` on the `td.available` cell inside the `.drp-calendar` whose `.month` reads e.g. `Nov 2026`, re-query the cell before each click (cells re-render), and click `.applyBtn` on that picker's own `container`. Click `#submit`, wait for `li.flight` cards, and confirm each card shows the requested dates. Treat it as a Kiwi-backed discovery family; its checked-bag filter is a candidate signal only - qualify any candidate at checkout or in the airline family.
- **ITA Matrix (full path only, optional).** Corroborate fares/schedules, not booking or bag; keep checked-bag qualification unverified until a completed provider or airline fare proves it.

## Provenance of user-observed recipes

The Google `?q=` link and the TAP deep link come from a dated user test on 2026-09-23 and are preserved for provenance, not presented as current verified fares. Revalidate them live (decline cookies, confirm route/dates/cabin, confirm populated results) before relying on them. Do not invent validation for them and do not promote them to stable APIs.

## Final check before reporting

- Route, dates, travelers and cabin on every recorded page match the search contract.
- Every shortlisted price carries a bag state: included, fee required, or unverified.
- Every shortlisted outbound and return is within the per-direction duration cap.
- Every source has a URL (or connector query) and a retrieval time with timezone; blocked sources are named.
- Only the requested cabins are reported, and the chosen path (quick or full) plus any deliberate skips are stated.

## Output

Start with assumptions, matched date windows, event buffer, and retrieval timestamp. Give compact sections for the requested cabins only, each with price, airlines, route, local times, stops/duration, cabin integrity, and baggage state. Route hacks go in a separate comparison. Preserve original currencies; any comparison conversion is clearly labelled with the exchange rate and its date, and is not presented as a bookable quote. End with up to 3-5 ranked recommendations and direct search/booking links. Distinguish live exact-date quotes from policy or deal-page evidence.

## Honesty and limits

Public flight sites commonly block automated sessions; source availability changes, so recheck once per run and never depend on a homepage loading as proof the search flow works. Airline deep links (e.g. the TAP recipe) are dated user-observed starting points, not guaranteed stable APIs; verify each render and reprice every run. Do not extrapolate one airline's observed behavior to another. This skill performs research only - it does not book flights, handle payments, store credentials, or guarantee observed prices. Treat historical dated examples as provenance, not current fares.
